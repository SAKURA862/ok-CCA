交错战线 · 全局启动层设计

目标：任何任务在执行前都先经过「启动游戏 / 处理登录页」；不改 ok-script 本体，只改项目自己的框架层（MyBaseTask 一处 + 新增模块）。

一、架构图

调用 绕过 / 实现关系 粉色：本次新增或改动的项目框架层
  • 为什么钩子在 run()：GUI、CLI 走 start_controller → TaskExecutor → task.run()；MCP 的 mcp_runner 绕开调度器，直接调用 task.run()。三条路径唯一的交集就是 run()。
  • 入口差异只影响“什么时候进入 run”：批量、单跑、CLI、MCP 最终命中同一个包装层，启动逻辑只写一份。
  • 不动 ok-script 本体：设备层、调度器、截图与点击 API 全部保持原样，只在项目基类里包一层。

二、类图

依赖（调用） 实现 / 弱依赖 △ 空心三角：继承
  • MyBaseTask.__init_subclass__ 用 functools.wraps 包装子类 run，函数名、签名、同步属性保持不变，MCP 运行器的校验（非 BaseTask.run、非 async/generator）依然通过。
  • BootstrapRunner 只依赖 GameAdapter 接口；加第二个游戏时新增一个适配器并在 config.game_profile 里切换，启动编排代码不用动。
  • 任务自身的 reset_to_start / verify_start_state 保留，但语义变为「确认可执行」，不再清场；MCP 的 reset → verify → run 流程因此不会关掉正在运行的游戏。
三个必然结论： 1. 启动步骤只写一次，位置在项目基类，不漏任何入口； 2. ok-script 包零改动，升级安全； 3. 是否启动 / 是否点击由运行时状态决定（前台包名 + 登录页特征），不做「每次重启」的粗暴处理。
